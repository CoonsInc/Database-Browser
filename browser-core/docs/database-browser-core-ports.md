# Database Browser: интерфейсы core.port

Статус: предлагаемое разделение интерфейсов на основе архитектуры и UC-1–UC-15. Имена методов описывают контракты; полные Java-сигнатуры уточняются при реализации.

## Назначение портов

`core.port` содержит интерфейсы внешних операций, необходимых сценариям приложения. Их вызывает `core.application`, а реализуют адаптеры `browser-sqlite` и `browser-io`. Позднее те же контракты реализуют адаптеры PostgreSQL и MySQL.

Один юзкейс может использовать несколько портов. Например, экспорт DDL получает SQL через адаптер БД, затем сохраняет его через файловый адаптер.

Во все операции с БД передаётся `sessionId`, кроме открытия подключения. Для краткости в таблицах он указан только у методов управления подключением. Идентификаторы результатов и операций также привязаны к своей сессии.

## 1. ConnectionPort — подключение к БД

**Связь с юзкейсами:** UC-1; дополнительно — проверка и закрытие подключения.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `connect(settings)` | Проверить параметры, открыть подключение и вернуть идентификатор сессии. |
| `checkConnection(sessionId)` | Проверить работоспособность открытого подключения. |
| `disconnect(sessionId)` | Закрыть подключение и освободить связанные ресурсы. |

Список открытых сессий и выбор адаптера находятся в `core.application`. Особенности открытия и настройки соединения находятся в адаптере.

## 2. DatabaseInfoPort — возможности СУБД

**Связь с юзкейсами:** редакторы схемы UC-3–UC-9, SQL-консоль UC-11–UC-13, план запроса UC-15.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `getDatabaseInfo()` | Получить название и версию СУБД. |
| `getCapabilities()` | Получить поддерживаемые возможности: изменения схемы, транзакции, планы запросов и другие. |
| `getSupportedTypes()` | Получить типы данных и их параметры для редактора колонок. |

Возможности описывают общую поддержку операций. Выполнимость конкретного изменения определяется при подготовке плана с учётом схемы и данных.

## 3. SchemaReaderPort — чтение структуры БД

**Связь с юзкейсами:** UC-2; зависимости в UC-5, UC-7, UC-13; подсказки SQL-редактора в UC-11–UC-13.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `readSchema()` | Получить снимок схемы: таблицы, колонки, ограничения, индексы, представления и триггеры. |
| `readObjectDefinition(objectId)` | Получить подробное описание объекта и его исходное SQL-определение. |
| `findDependencies(objectId)` | Найти объекты, от которых зависит выбранный объект, и объекты, зависящие от него. |

Если зависимости невозможно определить полностью, результат должен явно сообщать об этом. Обновление дерева объектов — повторное чтение схемы из сервиса core, затем обновление состояния UI.

## 4. SchemaChangePort — изменение схемы

**Связь с юзкейсами:** UC-3–UC-9; дополнительно — изменения колонок и представлений, предусмотренные архитектурой.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `prepareChange(request)` | Подготовить `ChangePlan`: SQL, проверки данных, зависимости, предупреждения и возможности отката. БД не изменяется. |
| `applyChange(plan)` | Проверить актуальность подтверждённого плана и выполнить его. При конфликте вернуть причину. |

`SchemaChangeRequest` описывает конкретное намерение:

- создать или удалить таблицу;
- добавить, изменить или удалить колонку;
- добавить или удалить ограничение;
- создать или удалить индекс;
- создать, изменить или удалить представление.

Отдельный метод порта на каждое намерение пока не требуется: различия выражаются типами запросов на изменение. Адаптер выбирает прямое DDL или миграцию с пересозданием таблицы.

План привязан к сессии и снимку схемы. Повторная проверка и выполнение происходят под необходимой защитой от конкурентных изменений. Нельзя незаметно заменить подтверждённый план другим. Во время ожидания подтверждения блокировка не удерживается.

## 5. SqlExecutionPort — выполнение SQL

**Связь с юзкейсами:** UC-11–UC-13; источник строк для UC-14.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `execute(request)` | Выполнить SQL с параметрами и настройками: таймаутом, режимом транзакции и ограничением выдачи. Вернуть сведения о выполнении и, при наличии строк, идентификатор открытого результата. |
| `fetchRows(resultId, batchSize)` | Получить следующую порцию строк открытого результата и признак окончания. |
| `cancel(operationId)` | Запросить отмену выполняющейся операции. |
| `closeResult(resultId)` | Закрыть результат и освободить ресурсы, например при закрытии вкладки. |

`operationId` задаётся до запуска, чтобы отмена была доступна во время выполнения. Запрос отмены может завершиться позже; итоговый статус сообщает, что произошло фактически.

Результат содержит описание колонок, число затронутых строк, время и предупреждения. Значения строк сохраняют типы. Полученное количество строк и общее количество строк — разные показатели; общее количество может быть неизвестно.

Ограничение выдачи не означает автоматическое добавление `LIMIT` к произвольному SQL. Политика транзакции задаётся явно; фиксация и откат выполняются адаптером в рамках операции. Для MVP с автоматическими транзакциями отдельный `TransactionPort` не требуется. Ручные транзакции пользователя потребуют дополнительного контракта.

## 6. QueryPlanPort — план запроса

**Связь с юзкейсами:** UC-15.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `explain(request)` | Получить план в общей модели и сохранить исходный вывод СУБД. |

Получение EXPLAIN и разбор специфичного вывода выполняет адаптер. Неизвестные узлы сохраняются. Режим с фактическим выполнением запроса, если он понадобится, следует явно отделить от обычного просмотра плана.

## 7. DdlExportPort — формирование DDL

**Связь с юзкейсами:** UC-10.

**Реализация:** адаптер соответствующей СУБД.

| Метод | Назначение |
|---|---|
| `generateDdl(schemaSnapshot, options)` | Сформировать DDL выбранных объектов или всей схемы в диалекте исходной СУБД с учётом зависимостей. |

Результат — SQL-текст для просмотра или сохранения. Снимок должен содержать исходные определения и сведения о диалекте; отсутствующие сведения нельзя молча заменять предположениями.

## 8. TextFilePort — сохранение текста

**Связь с юзкейсами:** UC-10.

**Реализация:** `browser-io`.

| Метод | Назначение |
|---|---|
| `writeText(target, text, options)` | Сохранить текст с указанной кодировкой и правилом перезаписи. |

Диалог выбора файла остаётся в JavaFX. Порт получает уже выбранное место сохранения.

## 9. CsvExportPort — потоковая запись CSV

**Связь с юзкейсами:** UC-14.

**Реализация:** `browser-io`.

| Метод | Назначение |
|---|---|
| `exportCsv(rowSource, target, options)` | Последовательно читать строки из источника и записывать CSV с заданными заголовками, разделителем, кодировкой и представлением `NULL`. |

`rowSource` — интерфейс источника типизированных строк без JDBC-зависимостей. Он позволяет передавать данные порциями. Контракт источника должен определять чтение и освобождение ресурсов; сервис экспорта закрывает принадлежащие ему ресурсы и при успехе, и при ошибке.

CSV-порт самостоятельно не выполняет SQL. Если пользователь должен экспортировать весь результат после частичной загрузки в UI, сервис обязан располагать источником полного результата. Повторное выполнение запроса допускается только как явно выбранное действие.

## Связь юзкейсов и портов

| Юзкейс | Основные порты |
|---|---|
| UC-1: подключение | `ConnectionPort` |
| UC-2: просмотр структуры | `SchemaReaderPort` |
| UC-3–UC-9: изменение схемы через редакторы | `SchemaReaderPort`, `DatabaseInfoPort`, `SchemaChangePort` |
| UC-10: экспорт DDL | `SchemaReaderPort`, `DdlExportPort`, `TextFilePort` |
| UC-11–UC-12: SELECT и DML | `SqlExecutionPort`; `SchemaReaderPort` для подсказок |
| UC-13: произвольный DDL | `SqlExecutionPort`, `SchemaReaderPort`; анализ зависимостей требует отдельно оговорённых границ |
| UC-14: экспорт результата в CSV | `CsvExportPort`; `SqlExecutionPort`, если источник читает открытый результат |
| UC-15: просмотр плана | `QueryPlanPort` |

Графический редактор передаёт структурированное намерение в `SchemaChangePort`. Произвольный SQL из консоли выполняется через `SqlExecutionPort`. Полный анализ последствий произвольного SQL не следует считать автоматически решённым наличием этих портов.

## Что уточнить или добавить в юзкейсы

| Пробел | Необходимое уточнение |
|---|---|
| Жизненный цикл подключений | Отключение, потеря соединения, закрытие приложения при активных операциях. |
| Большие результаты | Догрузка строк, отмена, таймаут и освобождение результата при закрытии вкладки. |
| Объём CSV | Экспорт загруженных строк или всего результата; поведение при закрытом или ограниченном источнике. |
| Изменения схемы | Изменение и удаление колонок, создание, изменение и удаление представлений. |
| Конкурентные изменения | Действия при изменении схемы или данных между preview и подтверждением. |
| Зависимости | UC-5 и UC-7 допускают подтверждение после предупреждения, а UC-13 требует блокировки. Нужна единая политика. |
| Произвольный SQL | Границы анализа зависимостей и поведения для неизвестных команд; классификатор не гарантирует безопасность. |
| Настройка подключения | Режим чтения, таймаут ожидания блокировки и политика WAL вместо неявных универсальных настроек. |

## Общие правила контрактов

- Порты используют модели core; `Connection`, `ResultSet`, `SQLException` и типы JavaFX остаются за границей core.
- Ошибки имеют общие категории и сохраняют исходную диагностику СУБД или файловой системы.
- Классификатор SQL, общие проверки и подготовка подсказок могут быть обычными компонентами core. Порт нужен для обращения к внешней возможности.
- Фоновые задачи запускаются вне JavaFX-потока; UI обращается к сервисам `core.application`.
- При закрытии сессии освобождаются её операции и результаты. Несколько сессий не смешивают результаты и транзакции.
- При миграциях сохраняются связанные объекты и исходные определения. Неподдерживаемое изменение отклоняется с объяснением.

## Первый этап реализации

Начать с `ConnectionPort`, `SchemaReaderPort` и `SqlExecutionPort`: подключение к SQLite → дерево схемы → выполнение SQL → результат порциями.

Следующий шаг — `DatabaseInfoPort` и `SchemaChangePort`: создание таблицы через preview и применение подтверждённого плана. После этого — планы запросов и экспорт.
